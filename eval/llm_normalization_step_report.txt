DESIGN
Pipeline: deterministic tokenize -> explode blocks into classifiable units
(list blocks split into individual items) -> optional LLM relabeling
(batched, sequential, carrying a heading-stack context forward) -> reassemble
blocks using the ORIGINAL text + new label -> render Markdown -> save.

Core safety property: the LLM receives only numbered text previews and
returns ONLY {index, label} JSON pairs -- it never outputs document text.
Our code always splices back the original, untouched block text. This makes
content mutation structurally impossible, not just something we check for
afterward. Validation is mostly schema-level (clean JSON, exactly one label
per index, no duplicates/out-of-range, label in the allowed enum) rather
than fuzzy text-similarity diffing.
Fallback is per-batch: one bad batch reverts only its own units to their
deterministic labels, not the whole document.
Trigger: runs only if ENABLE_LLM_NORMALIZATION=true AND (forced OR
structure_confidence is low/medium); never runs on high-confidence docs;
skips automatically if estimated batch count exceeds the cap (unless forced).

HONEST ASSESSMENT
The safety design is fully validated: across 145 classified units and 9 real
LLM batches, content preservation was perfect. The label-only architecture
worked exactly as intended -- zero content mutation even though the model's
labeling itself was imperfect. On label QUALITY: the two originally-reported
issues are reliably fixed. But the LLM pass also introduced new structural
inconsistencies absent from the deterministic-only output (duplicate title,
heading-level drift, inconsistent treatment of repeated framework labels).
Net structural quality on this one real document is a mixed improvement, not
a clean win. This is exactly the predicted risk from the Step 2.5 plan ("a
wrong label is still possible; quality risk, not corruption risk") -- and
exactly why ENABLE_LLM_NORMALIZATION defaults to off pending your review,
rather than being enabled automatically.
